1. 诊断工具箱 (Diagnostic Toolkit)

在通过各种渠道寻求帮助前，请先掌握以下三个核心调试工具：

1.1 详细模式 (Verbose Mode)

这是最强大的调试工具。通过将命令中的分隔符 - 替换为 +，Wish 会输出详细的执行日志。

# 普通模式（静默）
wish python=3.10 - python script.py

# 详细模式（调试）
wish python=3.10 + python script.py

日志包含的关键信息：

  • Setup Path: 正在加载哪个具体的 package.py 文件。
  • Relation Info: 依赖关系图及求解器的决策过程。
  • Execution Time: 各阶段耗时，用于性能分析。

1.2 打印调试 (Print Debugging)

由于 package.py 是标准 Python 代码，你可以在其中插入打印语句来调试执行逻辑。建议输出到 stderr 以避免干扰管道操作。

import sys
# 在 package.py 中
sys.stderr.write(f"DEBUG: Loaded {this.name}, init={this.init}\n")

1.3 开发者模式 (Develop Mode)

如果你正在开发一个新的包，可以使用 WISH_DEVELOP_MODE=1 并配合 WISH_DEVELOP_PATH 来优先加载本地未发布的包。

2. 核心流程诊断

2.1 解析阶段故障 (Resolution Phase)

症状: 报错 RESOLVE_ERROR，提示 "Cannot resolve conditions"。

深度分析日志:

在 wish + 的输出中，寻找 [Relation and Error Info] 块。这是一个 JSON 结构的转储。

[Relation and Error Info]
{
  ('my-tool', '1.0'): {
    'req': ['lib-a>=2.0'],
    'error': {
      'missing': ['lib-a'] 
    }
  }
}

常见错误类型解读:

  • missing:
    • 原因 1: 依赖包在仓库中完全不存在。 -> 运行 wish search lib-a 确认。
    • 原因 2: 存在该包，但没有版本满足约束（如仓库里只有 1.0，你要求 >=2.0）。 -> 检查版本约束。
    • 原因 3: 平台不匹配（Linux 上找不到 Windows 包）。 -> 检查 ava 条件。
  • conflict:
    • 原因: 显式的 ban() 规则或 xor() 互斥被触发。
    • 排查: 向上追溯，看是谁引入了冲突的包。

2.2 同步阶段故障 (Sync Phase)

症状: NETWORK_ERROR 或下载卡顿。

排查步骤:

  1. 检查 API 连接: curl $WISH_RESTAPI_URL/api/hello
  2. 检查 ETag: 如果日志显示不断重复下载同一个包，可能是服务端 ETag 配置错误或本地 SQLite 缓存文件损坏。尝试删除 ~/.wish/caches/manifest.db。
  3. 锁文件僵死: 如果一直卡在 "Wait 1s for download..."，检查 WISH_PACKAGE_PATH 下是否有残留的 .lock 文件并手动删除。

2.3 执行阶段故障 (Execution Phase)

症状: Wish 成功退出，但后续命令报错（如 Command not found 或 ImportError）。

原因: 环境变量未正确设置。

排查方法:

进入交互式 Shell 检查实际环境：

# 1. 进入环境 shell
wish my-pkg - bash

# 2. 检查关键变量
echo $PATH
echo $PYTHONPATH

# 3. 检查包路径
ls -l /path/to/my-pkg

常见陷阱:

  • 使用了 append 而不是 insert，导致系统自带的旧版本库被优先加载。
  • package.py 中使用了相对路径而不是 this.root。

2.4 环境继承诊断 (Environment Inheritance)

症状 A: "为什么我的子环境里有父环境的包？" (环境污染)

  • 原因: WISH_INHERIT_MODE 可能被意外设置为 "1"。
  • 检查: 运行 echo $WISH_INHERIT_MODE。
  • 修复: 显式设置 env("WISH_INHERIT_MODE").setenv("0") 在你的 package.py 中，或在命令行 unset WISH_INHERIT_MODE。

症状 B: "为什么我的宿主插件丢失了？" (过度隔离)

  • 原因: 这是一个常见陷阱。Wish 默认 (mode=0) 会通过 clear_inherit 机制清理掉所有未显式声明的父环境路径。
  • 修复: 参照 最佳实践 中的 "环境穿透模式"，开启继承模式。

3. 错误代码速查表

代码 错误名称 典型症状 潜在根因 (Root Cause) 修复建议 (Action)
1 NO_PARAM 仅输出帮助信息 用户未提供包名参数 检查命令格式，如 wish python
2 CONFIG_ERROR SyntaxError 或解析失败 package.py 语法错误或包含非法 Python 代码 检查 package.py 语法，确保没有使用未导入的模块
3 NETWORK_ERROR "Can not resolve network" 所有 API 节点及备用节点均不可达 1. 检查网络连接
2. 检查 WISH_RESTAPI_URL 配置
3. 尝试离线模式 WISH_OFFLINE_MODE=1
4 SPECPATH_ERROR "Specified path error" 指定的本地路径不存在或无 package.py 确认 pkg@/path/to/pkg 路径正确且包含 package.py
5 RESOLVE_ERROR "Cannot resolve conditions" 依赖冲突，SAT 求解器无解 使用 wish + 查看详细冲突信息，分析 missing/conflict 原因
6 PENDING_ERROR "Failed to auto-activate extension" ext 扩展包的触发条件 (ava) 未满足 1. 检查 ext 包的 ava 条件
2. 确认主环境是否满足扩展要求
255 UNDEFINED 未知错误 内部逻辑异常或未捕获的 Python 异常 开启 wish + ... 获取完整堆栈并提交 Bug Report

4. 运维故障排查

4.1 缓存清理

如果遇到文件损坏或校验错误，可以尝试清理本地缓存。

  • 自动清理: DBManage 会自动清理超过 30 天 未使用的包。
  • 手动清理: 删除 WISH_STORAGE_PATH (默认 ~/.wish/caches) 下的对应目录。

4.2 高可用验证

验证 API 故障转移机制：

  1. 设置 WISH_RESTAPI_URL 为一个无效地址 (如 http://0.0.0.0)。
  2. 设置 WISH_RESTAPI_URL1 为有效地址。
  3. 运行 wish + python。
  4. 观察日志，应看到 "Network error, try next..." 类似字样，随后连接成功。

5. 寻求支持

如果上述步骤无法解决问题，请准备以下信息并联系开发团队：

  1. 复现命令 (完整的 wish + ... 命令)。
  2. 完整日志 (包含 [Relation and Error Info])。
  3. 当前环境 (操作系统、Wish 版本、Python 版本)。
