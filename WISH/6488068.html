1. 客户端配置

1.1 目录规划

建议的目录结构：

变量默认值建议路径说明

WISH_LOCAL脚本所在目录/opt/wishtools安装根目录

WISH_PACKAGE_PATH$WISH_LOCAL/packages/opt/wishtools/packages共享包目录

WISH_STORAGE_PATH~/.wishtools/caches/var/cache/wish/storage下载缓存 (建议大容量)

WISH_DEVELOP_PATH~/.wishtools/develops~/wish-dev个人开发包目录

1.2 环境变量配置

在 /etc/profile.d/wish.sh 或用户 .bashrc 中配置：


# 核心路径
export WISH_LOCAL="/opt/wishtools"
export PATH="$WISH_LOCAL:$PATH"

# 主仓库配置
export WISH_RESTAPI_URL="http://api.company.internal/graphs?access=KEY&secret=SEC"
export WISH_STORAGE_URL="http://s3.company.internal/bucket?access=KEY&secret=SEC"

1.3 高可用配置 (High Availability)

Wishtools 客户端支持自动故障转移。你可以在环境变量中配置多个备用节点（后缀 1-10）。


# 备用 API 节点 (当主节点不可达时尝试)
export WISH_RESTAPI_URL1="http://api-backup-1.company.internal/graphs?..."
export WISH_RESTAPI_URL2="http://api-backup-2.company.internal/graphs?..."

# 备用存储节点
export WISH_STORAGE_URL1="http://s3-backup-1.company.internal/bucket?..."
export WISH_STORAGE_URL2="http://s3-backup-2.company.internal/bucket?..."

系统会按顺序（无后缀 -> 1 -> 2 ... -> 10）轮询，直到连接成功。

2. 服务端部署架构 (Server-Side)

Wish 的后端架构基于经典的微服务设计，核心依赖于图数据库 (Graph DB) 和对象存储。

2.1 架构拓扑

[ Nginx Load Balancer ]
        |
        v
[ API Cluster (Python/FastAPI) ] <---> [ Redis Cache (Optional) ]
        |
        v
[ Graph Database (Neo4j) ]      [ Object Storage (S3/MinIO) ]

2.2 核心组件部署

2.2.1 图数据库 (Neo4j)

Wish 强依赖图数据库来存储包的依赖关系与血缘图谱。

  • 推荐版本: Neo4j 4.4 LTS 或 5.x
  • 推荐配置:
# docker-compose.yml
services:
  neo4j:
    image: neo4j:4.4-community
    ports:
      - "7474:7474" # HTTP
      - "7687:7687" # Bolt
    environment:
      - NEO4J_AUTH=neo4j/your-secret-password
      - NEO4J_dbms_memory_heap_initial__size=1G
      - NEO4J_dbms_memory_heap_max__size=4G
    volumes:
      - ./data:/data

2.2.2 元数据服务 (Wish API)

这是无状态的 Python 服务，建议通过 Docker 部署。

services:
  wish-api:
    image: wishtools/api:latest
    environment:
      - WISH_GRAPH_URL=bolt://neo4j:7687
      - WISH_GRAPH_AUTH=neo4j:your-secret-password
      - WISH_STORAGE_ENDPOINT=http://minio:9000
      - WISH_STORAGE_ACCESS_KEY=xxx
      - WISH_STORAGE_SECRET_KEY=xxx
    depends_on:
      - neo4j

2.3 初始化流程

首次部署后，必须执行初始化脚本以建立图谱约束和索引：

# 1. 创建唯一性约束 (防止重复包名)
cypher-shell -u neo4j -p password "CREATE CONSTRAINT ON (p:Package) ASSERT p.name IS UNIQUE"

# 2. 创建版本索引 (加速解析)
cypher-shell -u neo4j -p password "CREATE INDEX ON :Version(tag)"

3. 容量规划与性能优化 (Capacity Planning)

3.1 API 服务规格

API 服务主要处理元数据查询，属于计算密集型 + 读多写少。

  • 小型团队 (10-50人): 2 CPU / 4GB RAM
  • 中型团队 (50-200人): 4 CPU / 8GB RAM
  • 大型团队 (200+人): 8 CPU / 16GB RAM (建议集群部署)

3.2 S3 存储规格

存储服务处理大文件下载，属于IO 密集型 + 带宽敏感。

  • 带宽: 建议内网带宽 > 10Gbps。对于跨国团队，强烈建议配置 CDN 或 S3 跨区域复制。
  • 存储: 取决于包的数量和历史版本保留策略。一般预留 1TB - 10TB。

3.3 备份策略

数据类型频率方式恢复目标 (RPO)

元数据 (Graph DB)每日全量 + 实时 Binlog数据库快照< 1 小时

包文件 (S3 Objects)开启版本控制跨区域复制 (CRR)< 15 分钟

Package.py 源码每次提交Git 仓库0 (实时)

4. 全球多地协同架构

对于跨国团队（如上海、伦敦、洛杉矶），为了解决跨洋传输慢的问题，推荐采用主备复制架构。

4.1 架构拓扑

[Master Region: Shanghai]
    ├── REST API (Master DB)  <--- 所有元数据写入
    └── S3 Bucket (Master)    <--- 所有包文件上传
           │
           │ (S3 Cross-Region Replication)
           ▼
[Slave Region: Los Angeles]
    └── S3 Bucket (Slave)     <--- 只读镜像

4.2 客户端配置策略

利用 WISH 的多源回退机制，让不同地区的客户端优先连接本地节点。

上海办公室配置:

export WISH_RESTAPI_URL="http://sh-api.internal/graphs"
export WISH_STORAGE_URL="http://sh-s3.internal/bucket"

洛杉矶办公室配置:


# 元数据仍然连接上海 (流量极小)
export WISH_RESTAPI_URL="http://sh-api.internal/graphs"

# 文件下载连接本地 S3 镜像 (流量极大)
export WISH_STORAGE_URL="http://la-s3.internal/bucket"

# 如果本地 S3 挂了，回退到上海主节点
export WISH_STORAGE_URL1="http://sh-s3.internal/bucket"

5. 离线模式部署

在无法连接外网或内网服务器的隔离环境中使用 Wishtools。

5.1 准备离线包

在有网环境打包：


# 1. 下载所需包到本地缓存
./wish python requests numpy

# 2. 打包 packages 目录
tar -czf wish-offline.tar.gz -C $WISH_LOCAL packages

5.2 离线环境配置

1. 解压包到离线环境。

2. 设置离线模式环境变量：

export WISH_OFFLINE_MODE=1

启用离线模式后：

  • wish 将不再尝试连接 WISH_RESTAPI_URL。
  • 仅使用 WISH_PACKAGE_PATH 中的本地包。
  • 依赖解析仅基于本地 package.py。

6. 安全加固

6.1 权限控制

WISH 客户端本身不处理鉴权，安全性依赖于后端服务。

  • API 安全: 建议在 Nginx/Kong 网关层做 Basic Auth 或 IP 白名单。
  • S3 安全: 配置 IAM Policy，允许 GetObject 但禁止 PutObject（仅 CI/CD 账号有写权限）。

6.2 审计日志

监控 WISH_RESTAPI_URL 的访问日志，可以分析：

  • 哪些包被下载最多（热度分析）。
  • 哪些旧版本仍在使用（漏洞预警）。

7. 故障排查

  • Network Error: 检查 curl $WISH_RESTAPI_URL。
  • Lock Error: 如果进程崩溃导致 .lock 残留，运行 find $WISH_STORAGE_PATH -name "*.lock" -delete。
  • Hash Mismatch: 如果 S3 文件被篡改，客户端会抛出校验错误。需清理本地缓存并重新上传包。
