Package 编写完全指南

本文档详细介绍如何编写 wishtools 的包配置文件 package.py。这是定义环境的核心，支持强大的 DSL（领域特定语言）。

1. 核心概念：静态声明 vs 动态执行

⚠️ 至关重要：理解 WISH 的解析机制

WISH 的 package.py 解析分为两个完全独立的阶段：

1. 静态解析阶段 (Parsing Phase):

  • 机制: 使用 Python 的 ast 模块对代码进行静态分析。
  • 行为: 提取 req, ava, ban, xor, alt, ext 等 DSL 关键字的参数。
  • 限制: 完全忽略 Python 的控制流语句（如 if, for, try）。
  • 陷阱: 即使你写在 if False: 块中的 req()，也会被解析器提取并生效！
    import sys
    
    # ❌ 错误示例：试图用 Python 逻辑控制依赖
    if sys.platform == "win32":
        req("windows-only-lib") # 😱 错误！即使在 Linux 上，这行也会被解析器抓取！
    
    # ✅ 正确示例：使用 DSL 原语控制依赖
    # 让 WISH 的求解器来处理平台判断
    req("windows-only-lib")
    ava("platform=windows") # 只有在 Windows 平台，这个包才会被认为是"可用"的

2. 动态执行阶段 (Execution Phase):

  • 机制: 在环境构建完成后，使用 Python 的 exec() 执行 package.py。
  • 行为: 执行 env(), alias(), print() 以及其他标准 Python 代码。
  • 能力: 此时可以访问完整的 this 上下文和文件系统，进行环境变量注入、文件拷贝等操作。

---

2. 文件结构与规范

每个包版本目录下必须包含 package.py：

packages/
└── <package_name>/
    └── <version_tag>/
        ├── package.py      # [必须] 包定义逻辑
        ├── src/            # [建议] 源代码或二进制
        └── LICENSE         # [可选]

2. 内置对象详解

2.1 this 对象

this 对象提供了当前包的上下文信息。

属性/方法类型说明示例
:---:---:---:---
this.namestr包名称"python"
this.tagsstr版本标签"3.10.6.1.lin.0"
this.rootstr包的绝对路径/opt/packages/python/3.10...
this.initbool是否首次初始化True 或 False

2.2 env() 函数

env(name) 返回环境变量操作对象。支持链式调用，修改仅在当前 Wish 会话中生效。

优先级规则:

环境变量是列表结构（以 : 或 ; 分隔）。操作顺序决定了查找优先级。

方法行为优先级适用场景
:---:---:---:---
insert(*paths)头部插入High (最先被搜索)主程序 bin 目录、优先使用的库
append(*paths)尾部追加Low (最后被搜索)备用路径、默认系统路径
setenv(*val)完全覆盖N/A版本号变量、标记位

示例:

# 确保本包的 python 优先于系统自带的 python
env("PATH").insert(os.path.join(this.root, "bin"))

# 将 man 手册路径添加到末尾
env("MANPATH").append(os.path.join(this.root, "share", "man"))

3. 依赖声明关键字

3.0 决策指南：我该用哪个关键字？

ASCII Flowchart
[ 起点: 我需要声明一个依赖 ]
       |
       V
< 必须有它才能运行? >
  |
  +-- NO --> < 是可选插件? >
  |             |
  |             +-- YES --> [ ext() ]  (扩展依赖)
  |             |
  |             +-- NO  --> [ ava() ]  (条件生效)
  |
  +-- YES --> < 需要互斥选择? >
                |
                +-- YES --> [ xor() ]  (二选一)
                |
                +-- NO  --> < 我提供通用接口? >
                              |
                              +-- YES --> [ alt() ]  (如 ssl-api)
                              |
                              +-- NO  --> [ req() ]  (标准依赖)

3.1 核心依赖 (req / ava / ext)

req(*pkgs) - 必需依赖

声明运行此包必须存在的依赖项。

  • 解析时机: 静态解析阶段。
  • 逻辑: AND 关系。所有列出的包必须同时满足。
  • 示例: req("python>=3.9", "numpy")

ava(*conditions) - 可用性条件 (Availability)

声明此包生效的前置条件。这是 WISH 中实现"条件依赖"的唯一方式。

  • 解析时机: 静态解析阶段。
  • 逻辑: OR 关系（只要满足任意一个条件组，包即视为可用）。
  • 常用模式:
  • 平台限制: ava("platform=linux", "arch=x86_64")
  • 宿主限制: ava("maya>=2022") (仅当依赖图中已存在 Maya 2022+ 时，此包才生效)
  • 组合限制: ava("platform=windows", "maya") (仅在 Windows 且有 Maya 时生效)

ext(*pkgs) - 扩展依赖

声明可选的、后置注入的依赖项。

  • 解析时机: 静态解析阶段。
  • 逻辑: 在主依赖树解析完成后，如果满足触发条件，则启动第二轮解析注入这些包。
  • 触发方式:
  • 环境变量: WISH_PACKAGE_EXTRA=pkg_name
  • 魔法后缀: ext("vray@maya") (如果环境中存在 maya，自动注入 vray)

3.2 冲突与变体 (ban / alt / xor)

ban(*pkgs) - 禁止冲突

声明与当前包不兼容的包。

  • 解析时机: 静态解析阶段。
  • 逻辑: NOT 关系。如果 banned 包存在，求解器会回溯并寻找其他解。
  • 示例: ban("pillow<9.0") (如果依赖图中必须有旧版 pillow，则当前包无法安装)

alt(*pkgs) - 替代提供 (Alternative)

声明当前包可以作为其他包的替代品。

  • 解析时机: 静态解析阶段。
  • 逻辑: Fallback 机制。当被替代的包（如 openssl）在仓库中不存在或无法满足版本要求时，求解器会尝试使用当前包。
  • 示例: alt("openssl==1.1.1") (我不仅是我，我还是 openssl 1.1.1)

xor(*pkgs) - 互斥选择

声明一组必须且只能选择其一的依赖。

  • 解析时机: 静态解析阶段。
  • 逻辑: XOR 关系。按顺序尝试，直到找到第一个不冲突的包。
  • 示例: xor("PySide6", "PyQt6") (优先用 PySide6，不行就用 PyQt6，但绝不能两个都装)

3.3 自动冲突消解 (Automatic Resolution)

Wish 的 SAT 求解器会自动处理传递性冲突。例如：

  • A 依赖 B=1.0
  • C 依赖 B=2.0

如果用户请求 wish A C，求解器会立即报告 UNSATISFIABLE，而不会像 pip 那样"后覆盖前"导致运行时错误。开发者无需手动编写复杂的检查逻辑。

4. 高级模式 (Power User Patterns)

package.py 不仅仅是一个配置文件，它是一个完整的 Python 运行环境。你可以利用 Python 的标准库和 this 对象的上下文来处理复杂的部署场景。

4.2 动态硬件适配 (Dynamic Hardware Adaptation)

利用 Python 代码检测宿主机硬件特性（如 CPU 指令集），并据此调整环境变量。

示例：根据 AVX512 支持情况加载优化库

import os

def has_cpu_flag(flag):
    try:
        with open('/proc/cpuinfo', 'r') as f:
            for line in f:
                if line.startswith('flags') and flag in line:
                    return True
    except:
        pass
    return False

src_path = os.path.join(this.root, "src")

if has_cpu_flag("avx512"):
    print("🚀 Power User: AVX512 detected. Enabling ultra-fast kernels.")
    env("LD_LIBRARY_PATH মলinsert(os.path.join(src_path, "lib-avx512"))
elif has_cpu_flag("avx2"):
    print("⚡ Power User: AVX2 detected. Enabling optimized kernels.")
    env("LD_LIBRARY_PATH").insert(os.path.join(src_path, "lib-avx2"))
else:
    print("⚠️ Power User: No advanced SIMD detected. Using generic kernels.")
    env("LD_LIBRARY_PATH").insert(os.path.join(src_path, "lib-generic"))

4.3 跨平台垫片 (Cross-Platform Shim)

在同一个 package.py 中优雅地处理 Windows 和 Linux 的差异。

注意：ava、req 等关键字是静态解析的，不受 if 语句控制。因此，不要尝试用 if sys.platform: 来包裹 ava，否则会导致包被同时标记为需要 Windows 和 Linux，从而无法解析。

正确做法：使用 Python 动态逻辑来处理环境变量和别名，而保持依赖声明的通用性（或创建两个独立的包版本）。

示例：统一的跨平台路径处理 (纯 Python 包或 NoArch 包)

import sys
import os

# 动态配置变量（运行时生效）
if sys.platform == "win32":
    # ava("platform=windows")  <-- 不要在这里写！静态解析会无视 if！
    # 如果必须区分平台包，请在文件系统中拆分为两个版本：
    # packages/mytool/1.0.0.win/... 和 packages/mytool/1.0.0.lin/...
    
    bin_subdir = "Scripts"
    lib_var = "PATH"
    ext = ".exe"
else:
    bin_subdir = "bin"
    lib_var = "LD_LIBRARY_PATH"
    ext = ""

# 应用配置
bin_path = os.path.join(this.root, "src", bin_subdir)
lib_path = os.path.join(this.root, "src", "lib")

env("PATH").insert(bin_path)
env(lib_var).insert(lib_path)

# 定义带后缀的别名
alias("mytool", os.path.join(bin_path, f"tool-core{ext}"))

4.4 首次运行钩子 (First-Run Hook)

this.init 属性在包第一次被加载到当前环境时为 True。你可以利用它执行耗时的初始化任务，如编译、解压或生成配置。

示例：自动编译着色器或资源

import os
import subprocess

if this.init:
    print("🔨 Power User: First run detected. Initializing workspace...")
    
    compile_script = os.path.join(this.root, "scripts", "compile_assets.sh")
    
    if os.path.exists(compile_script):
        # 执行初始化脚本
        result = os.system(f"bash {compile_script}")
        if result == 0:
            print("✨ Assets compiled successfully.")
        else:
            print("❌ Asset compilation failed.")

6. 实战代码模板 (Real-World Patterns)

6.1 Python 库 (PyPI 风格)

对于纯 Python 库，通常只需要将源码目录加入 PYTHONPATH。

# type: ignore
import os

# 1. 声明依赖 (映射自 requirements.txt)
req("requests>=2.0")
req("numpy")

# 2. 导出 Python 路径
# 假设源码解压在 src/ 目录下
env("PYTHONPATH").insert(os.path.join(this.root, "src"))

6.2 应用程序与服务 (App/Service)

对于大型应用（如 Neo4j, Java），通常需要配置 HOME 变量和 PATH。

import os

# 1. 运行时依赖
req("java>=11")

# 2. 定义关键路径
home_path = os.path.join(this.root, "src")
bin_path = os.path.join(home_path, "bin")
conf_path = os.path.join(home_path, "conf")

# 3. 设置环境变量
env("APP_HOME").setenv(home_path)
env("APP_CONF").setenv(conf_path)
env("PATH").insert(bin_path)

6.3 插件自动注入 (The Trigger Pattern)

利用 ext("plugin@host") 语法，实现"当宿主存在时，自动加载插件"的反转控制模式。

# package: ayon-init/package.py
import os

# 基础依赖
req("requests")

# 魔法扩展：
# 只有当依赖图中解析出 "maya" 包时，才会尝试加载 "ayon-init-maya"
ext("ayon-init-maya@maya")

# 只有当依赖图中解析出 "nuke" 包时，才会尝试加载 "ayon-init-nuke"
ext("ayon-init-nuke@nuke")

这种模式允许一个初始化包适配多种宿主，而无需强依赖它们。

6.4 系统桥接与回退 (System Bridge)

你可以编写一个"垫片包"，优先尝试使用宿主机已安装的软件，如果不存在则回退到 Wish 管理的版本。

# package: blender-launcher/package.py
import os

alt("blender=5.0")

sys_path = r"C:\Program Files\Blender Foundation\Blender 5.0"

if os.path.exists(sys_path):
    env("PATH").insert(sys_path)
    alias("blender", "blender --python-use-system-env")
else:
    # 开启环境继承模式，防止插件环境丢失
    env("WISH_INHERIT_MODE").setenv("1")
    alias("blender", "wish blender=5.0 + blender")

关于环境继承 (Environment Inheritance)

当触发回退机制（递归调用 wish）时，子进程会继承父进程的所有环境变量。这是一个特性而非 Bug：它保证了用户的基础工具（如 git, vim）在子环境中依然可用。但在深层嵌套调用时，需留意 PYTHONPATH 等累加型变量可能带来的干扰。

6.6 Python 模块化工具模式 (The Python Module Pattern)

场景：开发一个既可以用作命令行工具 (CLI)，又可以被其他 Python 脚本导入作为库使用的包（如 confflow）。

实现：采用标准 Python 包结构，利用 __main__.py 作为入口，并在 package.py 中配置 PYTHONPATH。

目录结构:

confflow/
├── package.py
└── src/
    └── confflow/
        ├── __init__.py    # 导出 API (get_page, ...)
        ├── __main__.py    # CLI 入口 (argparse logic)
        └── client.py      # 核心逻辑

Package.py 配置:

# package: confflow/package.py
import os

req("python>=3.6")

# 1. 暴露源码目录到 PYTHONPATH
# 这样用户既可以 `import confflow`，也可以 `python -m confflow`
env("PYTHONPATH").insert(os.path.join(this.root, "src"))

# 2. 设置可覆盖的默认配置
if not env("CONFLUENCE_URL").getenv():
    env("CONFLUENCE_URL").setenv("http://default.url")

# 3. 定义别名调用模块
# 相比直接调用脚本，这种方式更符合 Python 规范
alias("confflow", "python3 -m confflow")
alias("confluence-help", "python3 -m confflow --help")


7. Gitflow 包发布流程 (The Gitflow Workflow)

在企业级环境中，我们推荐使用 gitflow 包来管理 Wish 包的版本发布。它实现了代码与大文件 (LFS) 的分离管理。

7.1 核心机制

  • 自动化仓库初始化: 自动处理 git init 和 remote add，且默认使用 SSH 协议进行鉴权（需配置 ~/.ssh/id_ed25519）。
  • 智能 LFS 分离:
    • 在提交前，Gitflow 会扫描目录，自动将超过 50MB 的文件夹打包为 .pkgs 格式。
    • 大文件会被上传到 MinIO (通过 WISH_LFS_URL)，而在 Git 仓库中仅保留轻量级的索引文件 .pkgi (包含 ETag 和路径)。
  • 一键发布: 自动执行分支创建、代码提交和推送，大幅简化了发布流程。

7.2 使用范式

# 1. 确保开发模式开启
export WISH_DEVELOP_MODE=1

# 2. 使用 gitflow 推送包
# -d: 包所在的本地开发目录
# -g: GitLab 组名 (如 extra, tool)
# -p: 项目名称
wish gitflow - gitflow -d /path/to/my-pkg -g extra -p my-pkg

注意： gitflow 默认使用 SSH 协议连接 GitLab (`gitlab@gitlab.wish.net:group/project.git`)，请确保本地 SSH Key 已配置且拥有对应组的写权限。不要尝试在命令行中使用 HTTP Token 进行推送。
