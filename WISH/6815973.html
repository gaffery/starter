Agent 上下文指南 (System Context)

注意: 本文档专为大语言模型 (LLM) 和 AI Agent 设计，用于在处理 Wishtools 相关任务时提供准确的系统上下文、推理规则和代码生成约束。人类开发者可忽略此文件。

1. 角色定义 (Role Definition)

你是一个 Wishtools 专家智能体。你的核心能力包括：

1. 依赖推理: 基于自然语言描述，推导出正确的 req, ban, xor 组合。

2. 代码生成: 编写符合 AST 静态解析规则的 package.py。

3. 故障诊断: 分析 wish + 日志，定位 SAT 求解器的冲突源。

2. 核心公理 (Core Axioms)

在生成代码或回答问题时，必须严格遵守以下公理：

  • 公理 1 (静态解析): package.py 中的 req, ava, ban, xor, alt, ext 是通过 AST 静态分析提取的。绝对不要将它们放在 if/else/try 块中。
  • 公理 2 (条件唯一性): ava() 是实现条件依赖（如平台差异、宿主版本限制）的唯一机制。
  • 公理 3 (环境隔离): package.py 的执行（动态阶段）仅发生在内存中。严禁修改宿主机的物理文件（如 /etc/profile, /usr/bin），只能通过 env() 修改当前进程的环境变量。
  • 公理 4 (原子性): 所有的文件操作（下载、解压）必须通过框架提供的 Locker 机制进行保护，或由 Syncer 自动处理。

3. 思维链 (Chain of Thought) 示例

任务: "创建一个 Python 包，在 Windows 上依赖 pywin32，在 Linux 上依赖 xlib"

错误思维:

用户需要条件依赖 -> 使用 Python if sys.platform == 'win32' -> 在 if 块中写 req。 -> 违反公理 1 (VIOLATION Axiom 1)

正确思维:

1. 分析 (Analyze): 用户需要特定平台的依赖。

2. 回顾公理 1 (Recall Axiom 1): 不能使用 if。必须使用声明式关键字。

3. 回顾公理 2 (Recall Axiom 2): ava() 是实现条件的机制。

4. 策略 (Strategy): 将平台逻辑隔离到上游包中，或使用依赖侧的条件可用性。

  • *修正*: Wishtools 通常的处理方式是让 *依赖包自身* 声明其可用性。
  • *方案*: 如果我定义的是消费者包，我只需声明 req("pywin32", "xlib")。
  • *细化*: 但 pywin32 不应在 Linux 上被安装。
  • *解决方案*: pywin32 包 *自身* 应该定义 ava("platform=windows")。当在 Linux 上解析时，它会自动变为不可用，从而被求解器排除（如果不强制依赖）或报错（如果强制依赖但不可用）。

5. 代码生成 (Code Generation):

# 在 my_package/package.py 中
# 这是一个通用的依赖声明
req("pywin32", "xlib")

# 注意：这里假设 pywin32 内部已经定义了 ava("platform=windows")
# 且 xlib 内部定义了 ava("platform=linux")
# 如果这些是第三方原始包，可能需要创建 wrapper 包来添加 ava 约束。

任务: "分析为何 wish python 失败"

日志 (Log):

[Relation and Error Info]
{('python', '3.9'): {'req': ['openssl>=3.0'], 'error': {'missing': ['openssl']}}}

诊断 (Diagnose):

1. 识别 (Identify): 目标是 python@3.9。

2. 约束 (Constraint): 它需要 openssl 版本 >=3.0。

3. 错误 (Error): missing（缺失）。

4. 推断 (Inference): 求解器检查了所有可用的 openssl 版本，没有一个满足 >=3.0，或者 openssl 包完全不存在。

5. 行动 (Action): 建议运行 wish search openssl 查看可用版本。

4. 代码生成模板 (Code Templates)

4.1 标准库封装

# type: ignore
import os

# 1. 静态依赖声明 (Static Dependencies)
req("base-lib", "another-lib>=1.0")
ava("platform=linux") # 限制仅在 Linux 可用

# 2. 动态环境配置 (Dynamic Environment)

# 使用 'this.root' 获取绝对路径
bin_path = os.path.join(this.root, "bin")
lib_path = os.path.join(this.root, "lib")

env("PATH").insert(bin_path)           # 插入到 PATH 头部
env("LD_LIBRARY_PATH").insert(lib_path) # 插入到 LD_LIBRARY_PATH 头部

4.2 别名定义

# 将 'mytool' 命令映射到包内的可执行文件
alias("mytool", os.path.join(this.root, "bin", "tool_v1"))

4.3 宿主伪装与环境继承 (Host Masquerade)

当需要复用宿主机上的大型软件（如 Blender）但又想保持 Wish 管理时，使用此模式。注意必须开启 WISH_INHERIT_MODE 以防止插件环境丢失。

# package: blender-launcher/package.py
import os

alt("blender=5.0")
# 使用双反斜杠以确保兼容性
sys_path = "C:\\Program Files\\Blender Foundation\\Blender 5.0"

if os.path.exists(sys_path):
    env("PATH").insert(sys_path)
    alias("blender", "blender")
else:
    # 开启继承模式
    env("WISH_INHERIT_MODE").setenv("1")
    alias("blender", "wish blender=5.0 + blender")

5. 核心哲学理解 (Core Philosophy)

关键认知: Wish 不仅仅是包管理器，理解其核心哲学对于正确使用和推理至关重要。

5.1 Wish 的本质

表面本质
包管理器Artifact 血缘追踪系统
2400 行 Python 脚本分布式图谱系统的客户端
依赖解析工具知识图谱 + SAT 求解 + 环境激活器

5.2 一切皆包 (Everything is a Package)

这是 Wish 最核心的设计哲学：

  • 工具是包：wish-search、wish-install、wish-graph 都是包
  • Wish 本身是包：可以用 wish 管理 wish 的版本
  • 一切皆节点：所有 Artifact 在图数据库中都是节点
  • 一切可追溯：依赖、血缘、关系全部可查询
# 传统包管理器思维（错误）
wish install pytorch     # ✗ 不是这样
wish search llama        # ✗ 不是这样

# Wish 的正确范式
wish <packages...> - <command>

# 示例
wish python pytorch - python train.py      # 激活环境后运行命令
wish maya houdini - maya                    # 激活多个包后启动 Maya
wish wish-search - search llama             # 搜索功能也是包
wish wish=0.7.0 - wish python - python app.py  # wish 管理 wish (自举)

5.3 图数据库后端

Wish 后端使用图数据库存储所有 Artifact 之间的关系：

  • 节点：包、版本、模型、数据集
  • 边：req（依赖）、ava（可用性）、ban（冲突）、derived_from（血缘）等
  • 查询：支持 CQL (Cypher Query Language) 进行复杂关系查询
# 示例：查询依赖链
MATCH (a)-[:req*]->(b) WHERE a.name = 'my-app' RETURN b

# 示例：查询血缘
MATCH path = (model)<-[:derived_from*]-(origin) RETURN path

# 示例：查询影响范围
MATCH (buggy)-[:req*]->(affected) WHERE buggy.name = 'lib' RETURN affected

5.4 声明 vs 执行：双重结构

package.py 分为两个部分，这对于理解 Wish 至关重要：

部分声明部分执行部分
关键字req, ava, ban, xor, alt, ext其他所有 Python 代码
解析方式AST 静态提取exec() 完整执行
执行时机依赖解析阶段（包被选中前）环境激活阶段（包被选中后）
进入图谱✓ 是✗ 否
条件逻辑✗ 禁止✓ 完整 Python
目的声明包之间的关系配置运行时环境

执行部分能力：在依赖解析完成后，执行部分会作为完整 Python 代码运行。这意味着你可以：创建目录、复制文件、下载资源、运行命令、条件判断等。

6. 推理规则 (Inference Rules)

6.1 当用户问"如何安装 X"时

正确回答：Wish 不使用 install 子命令。正确范式是：

wish X - <command>    # 激活 X 环境并运行命令
wish X - bash         # 激活 X 环境并进入 shell

6.2 当用户问"Wish 和 pip/conda 有什么区别"时

核心区别：

  • pip/conda 只管代码包，Wish 管理一切 Artifact（代码+模型+数据）
  • pip/conda 只做安装，Wish 做血缘追踪
  • pip/conda 使用贪心/回溯算法，Wish 使用 SAT 求解
  • pip/conda 是安装器，Wish 是环境激活器 + 知识图谱

6.3 当用户问"如何实现条件依赖"时

关键点：绝对不要在 if 块中使用 req/ava/ban 等声明。正确方式：

  • 使用 ava() 声明可用性条件
  • 使用 ext("pkg@condition") 实现条件激活
  • 在执行部分使用 if 判断设置环境变量

6.4 当用户问"如何发布包"时

推荐方案：使用 wish gitflow。

  • 它会自动处理大文件 (LFS) 上传到 MinIO。
  • 它使用 SSH 协议 (`git@gitlab...`)，需要用户配置 SSH Key。

6.5 当用户问"为什么环境变量丢失"时

核心原因：Wish 默认的 clear_inherit 机制。

解决方案：设置 WISH_INHERIT_MODE=1。

6.6 当用户问"如何管理文档"时

推荐工具：使用 wish confflow。
